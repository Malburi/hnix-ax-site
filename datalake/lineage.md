# 계보 — 데이터가 어디서 와서 어디로 가나

계보는 원본(업무 DB·토픽·파일)에서 레이크 테이블·뷰를 거쳐 객체 유형과 **소비 경로**(화면·API·에이전트·AI 질문)까지 가는 길을 그래프로 보여 준다. 노드를 고르면 위·아래만 강조하고 **영향 범위**를 보여 준다 — "이 원본 테이블의 구조가 바뀌면 어디를 확인해야 하나".

## 무엇에서 만드나

계보를 따로 그리지 않는다. 이미 있는 기록에서 그때그때 만든다.

| 흐름 | 출처 |
|---|---|
| 원본 DB·Snowflake·REST·폴더 → 레이크 테이블 | 동기화 정의(마지막 실행 행 수·시각) |
| Kafka 토픽·HTTP 입구 → 테이블 | 스트림 정의(누적 행 수) |
| 올린 파일 → 테이블 | 파일 적재 기록 |
| 테이블 → 뷰 | 카탈로그의 뷰 정의(SQL 을 구조로 풀어 읽는 테이블을 뽑는다) |
| 테이블 → 파생 테이블 | 작업 SQL — `CREATE TABLE … AS`, `INSERT … SELECT`, `MERGE … USING` 을 실행할 때 기록(별칭·WITH·하위 조회를 구조 분석으로 가린다) |
| 테이블 → 객체 유형 | [온톨로지](/datalake/ontology.md) 정의 |
| 테이블 → 소비 경로 | 최근 30일 조회 이력 — 화면·API·에이전트(MCP)·AI 질문별 횟수·사람 수 |

## 보는 사람에 따라

- 엔지니어·관리자는 전체를 본다.
- 분석가는 **볼 수 있는 테이블과 그 앞뒤만** 본다. 권한 없는 원본·테이블 이름은 계보에도 나오지 않는다.

## 에이전트

MCP 도구 `table_lineage(schema, table)` 가 같은 내용을 글로 돌려준다 — 어디서 왔나(원본·변환)와 어디로 가나(파생·객체·소비 경로). 경보 진단 에이전트가 "이 테이블이 비었다"는 경보를 받으면 원본 동기화부터 거슬러 올라가는 데 쓴다.

## 남은 것

- 열 단위 계보(지금은 테이블 단위)
- 외부 BI 도구의 대시보드까지 잇기(지금은 API 키 단위 소비 경로)
