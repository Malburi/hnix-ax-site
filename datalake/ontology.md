# 온톨로지 — 업무 객체 · 관계 · 액션

레이크는 테이블을 모은다. 그런데 운영자와 에이전트가 묻는 것은 테이블이 아니라 **업무 객체**다.

- "이 장애가 난 서버에 최근 72시간 안에 들어간 변경은?"
- "결제 서비스 담당자는 누구고, 지난달 장애가 몇 건이었나?"

SQL 로는 조인과 시간 조건을 매번 새로 써야 한다. 온톨로지는 객체(장애·서비스·구성 요소·변경·담당자)와 관계(영향 서비스, 직전 변경)를 한 번 정의해 두고, 사람과 에이전트가 **SQL 없이** 따라가게 한다. 찾은 객체에서 바로 **액션**(진단 메모, 플랫폼 에이전트 요청)을 건다.

## 정의

| 정의 | 내용 | 예 |
|---|---|---|
| 객체 유형 | 레이크 테이블 하나 + 키 열 + 이름 열 + 보일 속성 | 장애 = `ito.incident`(키 `id`, 이름 `title`) |
| 관계 | 출발 유형 → 도착 유형. **열 = 열** 또는 **조건식**(a 는 출발, b 는 도착) | 장애 → 영향 서비스: `a.service_id = b.id` |
| | | 장애 → 직전 72시간 변경: `b.ci_id = a.ci_id AND b.ended_at BETWEEN a.opened_at - INTERVAL 72 HOUR AND a.opened_at` |
| 액션 | 대상 유형 · 방식(메모·웹훅) · 입력 항목 · 승인 필요 · 쓸 수 있는 역할 | 진단 메모 남기기, 진단 에이전트 요청 |

- 관계는 저장할 때 **한 번 엮어 본다** — 열 이름·타입이 틀리면 저장하지 않는다. 조건식에는 `;`·주석을 쓸 수 없다.
- 유형·관계는 엔지니어·관리자가, 액션은 **관리자만** 정의한다(웹훅은 데이터를 바깥으로 보내므로). 웹훅 토큰은 암호화해 둔다.

## ITO 표준 템플릿

'정의' 탭의 **ITO 표준 템플릿 설치** 한 번으로 통합ITO 운영에 맞춘 유형 7 · 관계 11 · 액션을 만든다. 시연 데이터 테이블(장애 300 · 변경 200 · 서비스 8 · 구성 요소 40 · 담당자 20 · 문제 15 · 서비스 요청 150)도 함께 만들 수 있다.

| 유형 | 테이블 | 관계 |
|---|---|---|
| 서비스 | `ito.service` | → 책임자 |
| 구성 요소 | `ito.ci` | → 소속 서비스 |
| 장애 | `ito.incident` | → 영향 서비스 · 발생 구성 요소 · 담당자 · 근본 문제 · **직전 72시간 변경** |
| 변경 | `ito.change` | → 대상 구성 요소 · 요청자 |
| 문제 | `ito.problem` | → 영향 서비스 |
| 서비스 요청 | `ito.sr` | → 대상 서비스 |
| 담당자 | `ito.person` | (연락처는 개인정보 — 가림 대상) |

고객 테이블의 이름·열이 다르면 설치한 뒤 '정의'에서 고친다. 테이블이 없는 유형은 건너뛰고 필요한 열을 알려 준다. 다시 설치해도 된다.

## 같은 규칙으로 읽는다

객체 찾기·보기·관계 따라가기·이웃 그래프는 모두 레이크 SELECT 로 바뀌어 [거버넌스](/datalake/governance.md)를 지난다.

- 조회 권한이 없는 테이블의 유형은 목록에도 없다.
- **행 제한**에 걸린 객체는 찾기·관계·그래프 어디에서도 나오지 않는다. 다른 소속 장애를 키로 열면 "없음"이다.
- **가린 열**은 속성·그래프에서도 가려진다 — 담당자 이름 `박*호`, 전화 `010-****-1234`.
- 객체 조회도 조회 이력에 `ontology` 로 남는다(누가 어느 길로 무엇을 읽었나).

## 액션 — 찾은 곳에서 바로 일을 시작한다

| 방식 | 하는 일 | 승인 |
|---|---|---|
| 메모 | 확인한 내용·추정 원인을 객체에 남긴다. **원본 데이터는 바꾸지 않는다** | 정의에 따라 |
| 웹훅 | 요청자가 본 객체(가린 값은 가린 채)와 입력을 JSON 으로 보낸다 — 플랫폼 에이전트 트리거·ITSM·메신저 | 정의에 따라 · **에이전트(MCP)가 요청하면 항상 승인 대기** |

- 승인은 엔지니어·관리자가 '실행 요청'에서 한다. **요청한 사람은 자기 요청을 승인할 수 없다.**
- 보내는 객체는 요청할 때의 모습을 저장해 둔다 — 승인한 사람의 권한으로 다시 읽지 않는다.
- 요청·승인·거절·결과는 모두 감사 기록에 남는다.

<figure><img src="img/datalake-actions.png" alt="실행 요청 — 진단 에이전트 요청(승인 대기, 승인·실행·거절 버튼)과 진단 메모 남기기(완료)"><figcaption>실행 요청. 분석가가 화면에서 한 요청과 에이전트가 MCP 로 한 요청이 같은 승인함에 쌓인다.</figcaption></figure>

> 원본 시스템을 고치는 쓰기(writeback)는 하지 않는다. 레이크는 원본의 사본이라, 원본에 대한 조치는 플랫폼 [런북](/platform/runbooks.md)·PMS-X 가 맡고 온톨로지 액션은 그쪽을 부른다.

## 에이전트 — MCP 도구

| 도구 | 하는 일 |
|---|---|
| `ontology_types` | 볼 수 있는 유형·관계·액션 — 먼저 부른다 |
| `find_objects` | 유형에서 이름·키로 찾기, 속성 조건(where) |
| `get_object` | 속성 · 관계별 개수 · 메모 |
| `linked_objects` | 관계를 따라간 객체 — 예: `incident_recent_change` |
| `propose_action` | 액션 제안 — 메모는 바로, 웹훅은 사람 승인 뒤. 이 도구만 읽기 전용이 아니다 |

통합 점검 ⑳ 이 실제로 돈다: 플랫폼 허브를 거친 에이전트가 P1 장애를 찾고 → 직전 72시간 변경을 따라가고 → 담당자 전화가 가려진 것을 확인하고 → 진단 요청을 제안(승인 대기) → 레이크 엔지니어가 승인하면 → 플랫폼 경보 진단 에이전트 웹훅이 202 로 받는다.
