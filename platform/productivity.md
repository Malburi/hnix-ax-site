# 생산성 보고서 — 커밋·SR·AI 관여

통합 유지보수 계약에는 "AI 도입으로 생산성 30% 향상" 같은 약정이 붙는다. Insight가 AI를 얼마나 썼는지 센다면, 생산성 보고서는 **그래서 일이 실제로 빨라졌는지**를 잰다. 저장소의 커밋·MR을 SR과 잇고, 기준선 대비 SR 1건당 공수와 리드타임이 얼마나 줄었는지 계산한다.

메뉴 "생산성 보고서"(관리자·감사자).

## 무엇을 모으나

| 자료 | 받는 길 | 남기는 것 |
|---|---|---|
| 커밋 | GitLab·GitHub 웹훅, 또는 수집 명령 `collect-git` | 메시지 첫 줄, 작성자, 시각, 브랜치, 변경 줄·파일 수 — **코드 본문은 받지 않는다** |
| MR·PR | GitLab Merge Request·GitHub Pull request 웹훅 | 제목, 상태, 원본 브랜치, 병합 시각 |
| SR(업무 항목) | PMS-X에서 가져오기, 또는 다른 ITSM이 API로 넣기 | 유형, 우선순위, 접수·해결 시각, 공수 |
| AI 사용 | Insight(게이트웨이·Claude Code·AX-NAVI) | 같은 SR 번호로 기록된 AI 호출 수와 비용 |

### 커밋 ↔ SR 연결

커밋 메시지, 브랜치 이름, MR 제목·설명에서 SR 번호를 찾는다. 기본 형식은 `SR-0012`, `SR-2026-0007`, `INC-101`, `CHG-…`, `CR-…`, `REQ-…`이고, 저장소마다 정규식으로 바꿀 수 있다(예: Jira `ABC-12`). `feature/SR-0101` 브랜치에서 만든 커밋은 메시지에 번호가 없어도 SR-0101에 이어진다.

### AI 관여

다음 중 하나라도 있으면 그 SR은 'AI 관여'로 본다.

- 커밋·MR의 표식 — `Co-Authored-By: Claude`, `Co-authored-by: Copilot`, `AI-Assisted: ax-navi` 같은 트레일러, "Generated with Claude Code" 문구
- 같은 SR 번호로 Insight에 들어온 AI 호출 — Claude Code 세션의 브랜치 이름, 게이트웨이 호출의 업무 번호

## 보고서 계산

대상은 기간 안에 **해결된** SR이다. 리드타임은 접수에서 해결까지, 공수는 PMS-X(또는 ITSM)에 기록된 값이다.

**유형 구성 보정** — 이번 달에 단순 문의가 많았다고 생산성이 오른 것처럼 보이면 안 된다. 그래서 SR마다 그 유형의 기준값을 기대치로 놓고 합을 비교한다.

```
기대 = Σ (각 SR 유형의 기준 평균)
절감률 = 1 − (실제 합 ÷ 기대 합)
```

| 기준선 | 언제 |
|---|---|
| 계약 기준값 | 계약 때 합의한 유형별 SR 1건 평균 공수·리드타임(예: 직전 연도 실적). 화면 "기준선·SR"에서 입력 |
| 기준 기간 실적 | 같은 시스템의 이전 기간(예: AI 도입 전 1년) 실적과 비교 |

보고서에는 공수 절감률, 리드타임 단축률, 목표 달성 여부, AI 관여 여부별·유형별 평균, SR 목록이 나온다. **마크다운**(월간 보고서에 붙이기)과 **CSV**(SR 목록)로 내려받는다.

### 해석 시 주의 — 보고서가 먼저 알려 준다

- 해결 SR이 20건 미만이면 통계로 말하기 어렵다.
- 커밋과 이어진 SR이 절반이 안 되면, 커밋 메시지·브랜치에 SR 번호를 넣는 규칙부터 확인한다.
- 기준선이 없는 유형, 공수가 기록되지 않은 SR은 비교에서 빠진다.
- 기간 커밋의 30% 넘게 업무 번호가 없으면 경고한다.

> AI 관여 SR과 그렇지 않은 SR의 평균 비교는 참고용이다. 어려운 SR에 AI를 더 쓰는 경향이 있으면 차이가 작게 나온다. 약정 판정은 유형 구성 보정 절감률로 한다.

## 저장소 연결

저장소를 등록하면 웹훅 주소와 비밀값이 한 번만 표시된다.

| 종류 | 설정 |
|---|---|
| GitLab | 프로젝트 → 설정 → 웹훅. URL, **Secret token**에 비밀값, Push events·Merge request events |
| GitHub | 저장소 → Settings → Webhooks. Content type `application/json`, Secret에 비밀값(서명 `X-Hub-Signature-256` 확인), Pushes·Pull requests |
| 일반 | 사내 Git이 플랫폼으로 나갈 수 없을 때. 개발 PC나 빌드 서버에서 수집 명령을 돌린다 |

```bash
hnix-ax collect-git --server https://ax.example.local --hook <저장소 id> \
  --token <비밀값> --repo D:\work\hr-legacy --since 30.days
```

같은 커밋을 다시 보내도 한 번만 남는다. 작성자 이메일이 플랫폼 계정 이메일과 같으면 계정과 잇는다. 다만 보고서는 SR 단위로 집계하고, 개인별 순위는 만들지 않는다.

## SR 가져오기

- **PMS-X** — MCP 허브에 등록한 PMS-X 연결(서비스 계정)과 프로젝트 ID를 고르면, SR의 유형·우선순위·상태·접수 시각·해결 시각(SLA 기록, 없으면 완료 상태의 갱신 시각)·공수를 가져온다.
- **다른 ITSM** — `POST /api/v1/delivery/work-items`에 `{ source, items: [{ key, type, createdAt, resolvedAt, effortHours, … }] }`를 보낸다. 같은 key는 갱신된다.
