# 모델 평가와 사내 GPU 모델 서버

어떤 모델이 통합 유지보수 업무에 충분한지는 범용 벤치마크가 아니라, 이 플랫폼이 모델에게 실제로 시키는 일로 재야 한다. 모델 평가는 게이트웨이의 모델 별칭 여러 개를 같은 정답 세트로 돌려 업무마다 쓸 모델을 고른다.

## 기본 정답 세트

| 세트 | 묻는 일 | 통과 기준 |
|---|---|---|
| SR 유형·우선순위 분류 (12건) | 요청 문장 → 유형 5종·우선순위 P1~P4 | 유형이 맞으면 통과. 점수는 유형 70% + 우선순위 30% |
| 근거 답변 (8건) | 번호 붙은 자료 안에서만 답하고 번호 달기 | 기대 근거 번호를 달았는가. 자료에 없으면 모른다고, 규칙을 어기라는 요청은 거절 |
| 도구 호출 (8건) | 요청에 맞는 도구를 맞는 인자로 | 도구 이름과 기대 인자 일치 |
| KB 초안 형식 (4건) | 처리 기록 → 정해진 네 절의 초안 | 증상·원인·조치·재발 방지가 모두 있는가 |

문장은 가상의 인사·급여·근태·구매 업무로 지었다. 실제 SR·문의로 만든 **사내 세트**는 같은 JSON 형식으로 올린다(개인정보는 지우고).

## 실행과 결과

- 별칭 1~8개와 세트를 고르면 사례마다 한 번씩 부른다. 호출은 실행한 관리자 권한으로 게이트웨이를 지나므로 예산·개인정보 규칙이 그대로 걸리고, 사용량은 Insight에 평가로 따로 쌓인다. 외부 모델이면 비용이 든다.
- 별칭 × 세트마다 통과율, 점수, 평균·p95 응답 시간, 토큰, 호출 오류를 보여 주고 사례별 출력과 실패 사유를 남긴다.
- **권장**: 세트마다 통과율 80%를 넘는 별칭 가운데 가장 빠른 것. 넘는 것이 없으면 통과율이 가장 높은 것을 '기준 미달'로 표시한다.
- **업무 별칭에 반영**: 권장 별칭의 대상 모델을 PMS-X·현업 창구·에이전트가 쓰는 업무 별칭으로 옮긴다. 감사 로그에 남는다.

> 사내 CPU 3B 모델의 기준선(2026-10): 분류 83%, 근거 답변 100%, 도구 호출 88%, KB 형식 100%. 기본 근거 세트는 쉬운 편이라 변별력은 사내 세트로 보강한다. 도구를 여러 번 이어 부르는 에이전트는 아직 세트에 없다.

## 사내 GPU 모델 서버 (vLLM)

플랫폼 저장소의 `deploy/vllm/`에 설치 꾸러미가 있다.

| 파일 | 내용 |
|---|---|
| `docker-compose.yml`, `.env.example` | 컨테이너로 띄우기 — 폐쇄망 환경 변수, API 키, 도구 호출 파서, GPU 설정 |
| `hnix-vllm.service` | 컨테이너 없이 파이썬 가상환경으로 띄울 때의 systemd 단위 |
| `check.mjs` | 띄운 뒤 점검 — 모델 목록, 한국어 답, 도구 호출, 응답 시간. 실패하면 종료 코드 1 |

| 모델 크기 | GPU 메모리(대략) | 쓰임 |
|---|---|---|
| 7~8B | 24GB 1장 | 분류·KB 초안·창구 답변 같은 단일 호출 |
| 14B | 48GB 1장 또는 24GB 2장 | 위 + 도구 2~3개짜리 에이전트 |
| 32B (4bit 양자화) | 48GB 1장 | 도구 여러 개 에이전트, 긴 문서 근거 답변 |

순서: 모델 반입(인터넷 PC에서 받아 해시 확인) → `docker compose up -d` → `node check.mjs` → 게이트웨이 프로바이더(OpenAI 호환, **사내 로컬** 켬)와 별칭 등록 → 모델 평가 → 업무 별칭에 반영. 모델 라이선스는 반입 전에 상업 이용 가능 여부를 확인한다.

```bash
node check.mjs --url http://gpu01:8000/v1 --key <API 키> --model itox-14b
```

> 점검 스크립트는 OpenAI 호환이면 무엇이든 확인한다. 시연용 3B 모델을 점검하자 한국어 질문에 일본어로 답하는 것을 잡아냈다.
